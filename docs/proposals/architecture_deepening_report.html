Nivesh Architecture Deepening Report

Improving testability & AI-navigability through module deepening — 7 candidates

June 2026 · backend FastAPI (3.1k LOC services) · iOS SwiftUI (~11k LOC)

1. Orchestrator God Module → Domain-Specific Deep Modules

STRONG
services/orchestrator.py services/confidence_engine.py services/quant_engine.py services/job_manager.py routers/analysis.py

Problem

orchestrator.py (1,827 lines) is the deepest module in the system — and that is the problem. The analyze() function (~590 lines) is a sequential monolith that chains 10+ operations: cache check, smart gate, yfinance prefetch, quant engine, LangGraph multi-agent, deep scan, calibration pipeline (8 parallel tasks), reformat with retry, normalization, extreme enrichment, DB save. Every caller (routers/analysis.py, services/job_manager.py, services/checkpoints.py) must route through this single function. The deletion test is brutal: deleting orchestrator.py does not reveal complexity in callers — it reveals total system collapse. The module is deep in behaviour but its interface (analyze(ticker, exchange, user_id, deep_scan, scan_type, job_id) → dict) is deceptively narrow — all the real complexity is hidden behind a single function signature that offers no hooks, no customization points, and no testing seams.

Solution

Split orchestrator into 4 domain-specific modules, each with a narrow interface and independent testability: CacheOrchestrator (cache check + smart gate logic), AgentOrchestrator (LangGraph setup + agent execution), CalibrationOrchestrator (8 parallel calibration tasks + final confidence), AnalysisPersister (DB save + advisor fetch). The analyze() function becomes a thin coordinator that composes these 4 modules in sequence, each injectable for testing.

  • Testability — Each sub-module can be tested in isolation by injecting a fake for its downstream dependency. CacheOrchestrator can be tested without LangGraph or yfinance. The coordinator can be integration-tested with mock sub-modules.
  • AI-navigability — A reader wanting to understand "confidence calibration" jumps to calibration_orchestrator.py instead of scrolling through 590 lines.

2. iOS Models.swift → Domain-Sliced Modules

STRONG
ios/…/Models.swift (2,470 loc)

Problem

A single file with 103+ structs, enums, and extensions. StockAnalysis (~80 fields) plus the full set of DTOs for 20+ API endpoints. The deletion test: deleting this file removes every data contract from the iOS app — no single struct is duplicated elsewhere, but every feature file imports from it. Understanding the data model for any one feature (e.g., dashboard) requires scrolling past 50 unrelated structs. Xcode's indexing slows on files over 2,000 lines. Merge conflicts are frequent. Every new endpoint requires adding a struct here, violating locality — the struct for OptionsPayoffResponse lives next to LoginRequest, even though they serve completely unrelated features.

Solution

Split into domain-specific model files: Models/PortfolioModels.swift, Models/AnalysisModels.swift, Models/MarketModels.swift, Models/AuthModels.swift, Models/EarningsModels.swift, Models/OptionsModels.swift, Models/Common.swift (shared primitives like Signal). The Models.swift file becomes a re-export umbrella.

3. helpers.py — Dissolve the Grab-Bag into Focused Modules

STRONG
backend/helpers.py (834 loc) backend/core/security.py backend/routers/analysis.py backend/config/settings.py

Problem

helpers.py is the canonical "everything else" module. It contains: rate limiting logic, Pydantic request models (14), Pydantic response models (4), yfinance wrappers (5 functions), ticker resolution with cache, NSE directory lookup, dashboard state (deques + locks), token logging, analysis concurrency management (slot acquire/release/cancel with per-user semaphores), auth dependencies (get_current_user_id, require_auth, require_admin), notification helpers, NSE ASM/GSM list fetching, and market index data. The deletion test: deleting helpers.py would spread complexity across 8+ router files and main.py. Its interface doesn't exist — everything is a top-level function or module-level variable. Importers reach in directly.

Solution

Extract into 5 focused modules: core/rate_limiter.py (all rate limiting), core/concurrency.py (analysis slot management, _running_analyses), services/yfinance_client.py (yfinance wrappers + ticker resolution), services/nse_client.py (NSE API calls, ASM/GSM, indices, directory), core/dashboard_state.py (all dashboard deques, locks, and dash_* functions). Request/response models stay in schemas/ (which already exists but is incomplete). Auth dependencies stay in core/security.py (already extracted).

4. iOS NetworkManager → Protocol-Based API Client

STRONG
ios/…/NetworkManager.swift (1,330 loc) ios/…/NetworkManager+Sidebar.swift (354 loc) ios/…/Models.swift

Problem

NetworkManager is a singleton class with ~45 API methods, each duplicating the same URLSession pattern: build URL, add auth header, add correlation ID, decode JSON, wrap error. There is no test seam — every ViewModel that needs network access must depend on the real singleton, making unit tests impossible without running the full server. The deletion test: removing NetworkManager would force every ViewModel to reimplement URLSession boilerplate. The interface is "all 45 methods" — there's no way to say "this ViewModel only needs portfolio methods."

Solution

Define a protocol APIClient with domain-grouped method requirements. Create the concrete URLSessionAPIClient adapter (the current implementation). ViewModels depend on APIClient via constructor injection. A second adapter (MockAPIClient or PreviewAPIClient) provides test/preview data. NetworkManager.shared becomes one adapter instance, not the sole authority.

5. Math Engines — Uniform Inference Seam

STRONG
services/math_engines/*.py (15 files) services/confidence_engine.py services/quant_engine.py services/orchestrator.py services/factor_engine.py

Problem

The 15 math engine files in services/math_engines/ each export 1-2 functions with completely different signatures. Some take a (ticker, session) pair, others take raw numpy arrays, others take a full StockAnalysis dict. They are called from at least 3 different orchestrators (orchestrator.py, confidence_engine.py, quant_engine.py). Identifying which engines run for a given analysis requires reading all 3 callers. Each engine has its own error handling pattern (try/except vs sentinel return values vs raising). There is no seam where a consumer says "run all applicable engines and give me the results" — the caller must know about each engine individually.

Solution

Define a uniform InferenceEngine protocol with a single method compute(ticker, analysis_data, session) → dict. Each engine (conformal, minsky, pcr_gex, etc.) becomes an adapter implementing this protocol. An EngineRegistry provides discovery: consumers ask for all engines that satisfy a capability tag (e.g., "risk_metric", "confidence_modifier", "valuation"). The calibration pipeline becomes a generic "run all engines tagged 'confidence_modifier' in parallel."

6. database.py — Separate Schema from Queries

Worth exploring
backend/database.py (1,181 loc)

Problem

database.py defines 24 SQLAlchemy ORM models AND all query/CUD functions (save_analysis, create_job, sweep_stale_jobs, etc.) in a single file. The interface is ~50 exported symbols ranging from table column definitions to multi-line query functions. Understanding "how does job creation work?" requires differentiating table columns from query logic. Every module imports from database.py — changing any one symbol risks side effects across 50+ import sites. The deletion test fails qualitatively: deleting database.py would break every service and router, but the complexity (24 tables + 30 query functions) is dense enough that it's earning its keep — it's just not well-structured.

Solution

Split into 3 files: models/__init__.py (24 ORM classes, column definitions only), database.py (engine, session factory, get_session(), init_db()), and repositories/analysis_repo.py + repositories/portfolio_repo.py + repositories/job_repo.py (query methods grouped by domain). The Phase 1 refactor comment ("extracted from main.py") already hints this was planned.

7. TradingAgents Fork — Isolate the Forked Package

Worth exploring
backend/tradingagents-core/ backend/main.py (lines 12-16) backend/services/orchestrator.py backend/.gitignore

Problem

The project vendors a full fork of the tradingagents PyPI package at backend/tradingagents-core/tradingagents/. On startup, main.py inserts this path into sys.path before any imports, shadowing the installed PyPI package. This creates a fragile build-time coupling: the fork must stay API-compatible with orchestrator.py's call sites, but diverges from upstream. 80+ files are tracked in git (force-added, were previously .gitignored). There is no CHANGELOG.md tracking what differs from upstream, no patch file, no branch strategy.

Solution

Three options, in decreasing order of preference: (1) Upstream the changes and remove the fork; (2) Use pip install -e ./tradingagents-core with a proper pyproject.toml version patch so the package is installable without sys.path manipulation; (3) Extract only the modified files (default_config.py, graph configuration) into a thin shim module in services/ that overrides specific behaviours at import time, deleting the rest of the fork.

  • Locality — The fork is an explicit dependency with a version, not a silent sys.path shadow.
  • Leverage — pip install -e ./tradingagents-core reduces main.py startup by 5 lines and eliminates an entire class of "works on server but not locally" bugs.
  • Testability — CI can pip-install the fork as a real dependency. No special path handling needed in test runners.
⚠️ The fork exists because orchestrator.py depends on tradingagents.config internals that diverge from PyPI. Option (3) — a thin shim — may be the safest path if upstreaming is not feasible.

8. HomeScreen — Feature-Sliced Decomposition

Speculative
ios/…/Views/HomeScreen.swift (3,082 loc)

Problem

At 3,082 lines, HomeScreen.swift is the largest file in the iOS app. It contains: the view model (data fetching, auto-refresh timer, debounce logic, state management), the main view layout (configurable section order via @AppStorage, NavigationStack with destinations), 30+ sub-views, pull-to-refresh, spotlight search, notification observers, and crash guard logic. The deletion test: removing HomeScreen.swift removes the app's primary screen — but the complexity is real (it is the home screen). The pain is in navigability: Xcode struggles with files over 2,500 lines, and finding any specific sub-view requires scrolling past 1,000+ lines or using "Jump to bar" with fuzzy search.

Solution

Extract into feature-sliced files under a Views/Home/ directory: HomeScreen.swift (thin layout shell, ~200 lines), HomeViewModel.swift (already separated in concept, move to dedicated file), HomeScreen+Sections.swift (section rendering), HomeScreen+Cards.swift (individual card views). The ~30 inline sub-views (NiveshBulletRow, PriorityPill, etc.) each get their own file. The section-ordering logic (HomeSectionID, activeSectionOrder) becomes a separate model.

Top Recommendation

Candidate 3: Dissolve helpers.py into focused modules — with Candidate 4: Protocol-based iOS API client as a close second.

Why helpers.py first: Every backend service, router, and main.py imports from helpers.py. Its dissolution into core/rate_limiter.py, core/concurrency.py, core/dashboard_state.py, services/yfinance_client.py, and services/nse_client.py is pure extraction — zero behavioural change, zero risk, mechanical refactoring. It pays dividends immediately: each new module is independently testable, AI-navigability improves because "find rate limiter" takes you to one 80-line file instead of scrolling past 400 lines of unrelated code, and it completes the Phase 1 refactor that was already started with schemas/ and core/security.py.

Estimated effort: 2-3 hours (1 session). 100% safe. Highest risk/reward ratio.
